# PR #73 実GPS・通常RUNのTest検証計画

提出日 2026-11-11。後続のユーザー指示で11月12日の150分RUNを優先し、A〜Dを前提条件から外した。今回の実施方針は[150分RUNの診断準備](issue73-longrun-20261112.md)を参照。この文書は段階比較計画として保持する。

対象はTest v30、APK内表示705a44c+journal-device-v30。第1段階の人工入力5,700件受入を前提とする。PR #73はDraft、Issue #72はOpen。Production配信、Auto Stop判定・GPS要求間隔の変更、他PRの変更、実停止マーカー、F方式比較は対象外。

## 1. 実装上の測定範囲

通常のSTARTからexpo-locationの背景タスク、src/tasks/location-task.tsのingestLocationBatch、RunRepository.appendActiveObservations、GpsObservationSession、detectStop、LatestCheckpoint、SQLiteのsaveDraft、通常の終了保存までを通す。人工入力ボタンは使わない。

Test版は位置更新1秒・距離間隔0を要求するが、OSの配信周期を保証する値ではない。SQLiteの通常GPS点は既存の5秒保存ゲートと終了flushに従う。1秒入力数と履歴GPS点数を等しくする基準は設けない。

診断の採取範囲はJS_SUBMITTED_ONLY。OS/provider内部で未配信の位置や、プロセス終了中の位置は直接数えられない。GPS時刻の間隔、コールバック間隔、配信遅延、バッチ件数で空白を記録し、原因が特定できないものは不明とする。端末の時刻変更が起きた区間は遅延比較から外し、欠測理由を残す。

## 2. データ保全と開始条件

- 既存の実RUNや未完了ドラフトがある場合は開始を保留し、内容を変更しない。
- 試験直前に全履歴・GPS・ごみ箱・設定・グループ・保護情報を含むBackupと保持音声ログをPC私有領域へ保存。APKハッシュ・署名・端末OS・設定・省電力状態・空き容量も記録する。過去の54履歴等の件数を固定前提にせず、その時点のsnapshotを基準とする。
- 新規Test RUNのIDを私有の台帳に記録し、試験後の差分として追加が許される対象を限定する。新規RUNは保持し、ごみ箱移動・削除・保持期限処理を起動しない。既存RUNごとの全データ、既存ごみ箱、既存グループ所属と保護情報は完全一致を要する。新しい試験RUNによる集計値の変化は追加データとして説明する。
- 現行のgetActiveRuns/getTrashedRunsは内部でpurgeTrashを呼ぶ。照合にこれらの一覧APIやごみ箱画面を使わず、Backup・getHistoryPage/getRunの非削除経路を使う。通常START・終了・再起動で通る画面の呼出し経路も実行前に確認し、期限処理へ入る経路があれば操作を保留して報告する。
- 各段階の後にバックアップを取得し、元データ部分の正規化比較を行う。不一致時は後続操作を停止し、証跡を保全する。元データを復元して合わせない。SQLiteの検査はPC側の隔離コピーで行い、端末DBへの直接更新・復元は行わない。
- 設定は原則そのまま使用し、現在の目標・自動終了が試験時間と競合する場合は実行前にその変更内容を提示する。音声、Auto Stop、目標等をON/OFF比較の間で変えない。診断だけをRUN開始前にON/OFFする。
- 屋外で安全な場所を使用する。PCから端末を物理的に移動できないため、移動・充電ケーブル着脱・必要なロック解除はユーザーが担当する。屋外移動の具体的な時間帯はレビュー後に調整する。

## 3. 段階ごとの手順と判定

| 段階 | 方法 | 合格基準 |
| --- | --- | --- |
| A 短時間・通常RUN | 同じ端末・安全な屋外区間でOFF/ON各8分。通常START→移動→安全な場所で静止→移動→通常終了。各条件で有効な配信入力300件以上を目安とし、満たなければ最大15分まで延長。SQLite保存・終了後の再起動読出しを確認 | ONは配信された入力の診断欠損0、受付拒否0、正常END・seal、全ページ認証・現行再生不一致0。SQLiteの点選択は同じ採取入力を既存5秒ゲート・終了flushで再計算して一致。履歴1件のみ追加、既存データ一致。OFFは診断ファイル新規作成なし。 |
| B Home背景・画面OFF | A合格後、OFF/ON各12分。画面ON 2分→Homeで別画面2分→画面OFF 6分→復帰2分。AppState、実画面状態、GPSタスク・前景サービス状態を区間ごとに記録 | 各区間で通常RUNとSQLite保存が継続し、ONのJS配信済み入力は全件記録、seal・再現一致。実画面OFFの証跡がある。復帰後に二重RUN・重複点・過去通知の滞留を生じない。 |
| C 強制Doze | B合格後、屋外の静止状態でOFF/ON各10分。画面OFF前後を含め、実Doze区間を5分以上確保。省電力除外の現状を維持。deviceidleのforce-idleと状態取得でDoze成立を確認し、必ずunforceして元状態へ戻す | Doze成立を実測。ONだけに追加の診断欠損・保存失敗がない。実際に配信された入力は全件整合。解除後、良好なGPS条件で30秒以内に受付・判定・checkpointが再開。OS配信が停止した区間はGPS空白として報告し、継続採取の合格とは扱わない。Doze未成立は未検証。 |
| D 負荷と電池の比較 | A〜C合格後、同条件の画面OFFでOFF→ON→ON→OFFの30分×4本。開始時刻・気象・端末温度・電池残量・音声/通信・携行方法を記録。開始電池は概ね40〜90%、充電せず、同等の初期温度で開始。必要に応じ冷却・充電待機を挟む | 下記の遅延・電池・温度・メモリ基準を満たす。短時間だけの電池%変化から持続時間を断定しない。ばらつきが大きい場合は判定保留。 |
| E 実時間の長時間採取 | D合格後、別RUNで診断ONの95分を段階的に確認。30分時点で容量と体調・温度・遅延を確認。移動量は無理をせず歩行・静止を含める | 95分間に実際に配信された入力を全件記録、拒否・診断欠損0、正常END・seal、全ページ認証と再現一致、履歴・SQLite整合。時刻の長さと実入力件数を両方報告し、必ず5,700件になるとは仮定しない。 |

Dozeの操作はAndroid公式の試験手順に従う。USB給電・ADB接続が省電力状態と消費電力に与える影響を記録する。強制Doze中の電池値はDの自然条件比較に混ぜない。設定の模擬unplugが必要な場合は実行前後を記録してbattery resetで解除し、計測値が模擬状態だった区間は電池評価から外す。操作やロック解除によってDozeが解除されたら成立時間を数え直す。

参考 https://developer.android.com/training/monitoring-device-state/doze-standby#testing_doze

## 4. 計測方法と暫定合格基準

以下はレビュー用の暫定値。条件・件数・欠測・ヒストグラム分解能を結果とともに示す。

| 項目 | 取得方法 | 暫定基準 |
| --- | --- | --- |
| 配信・欠損 | GPS_OBS_DELIVERED、STALE_OR_INVALID、評価数、バッチ数、INPUT.raws、ADMISSION、OUTPUT、Native writtenInputs、END totalsを私有領域で照合 | 正常ON RUNでは配信入力と記録INPUT件数が一致。重複・無効位置等はADMISSION理由と件数が一致。物理的な移動の正解率は評価しない。 |
| SQLite | STOP_CHECKPOINTの成功/失敗と時間、終了保存結果、保存済み点と再計算した保存対象点、再起動後の履歴を照合 | 正常終了RUNの保存失敗0、点の重複・未説明の欠落0。全既存データ一致。checkpoint統合により中間snapshot数が入力数より少なくなることは許容。 |
| 処理遅延 | STOP_PIPELINEのrepositoryWaitMs・evaluationMs、STOP_CHECKPOINT duration、Native write/queue、診断handoffのp50/p95/最大と件数。GPS配信遅延は別に集計 | 引渡しp95上限10ms。Repository待ちと評価処理のON p95増分はそれぞれmax(5ms, OFF p95の20%)以下。checkpoint p95増分はmax(50ms, OFF p95の20%)以下。Native待ちの最大値とoverflowを併記。 |
| 指標の網羅性 | STOP_PIPELINEは判定診断が生成された評価に限定され、全コールバックとは限らない。handoffSummaryも既存画面で全数取得できるか事前確認 | データがない指標は不明。全入力の遅延を測るため追加のTest限定集計が必要なら、実装内容を提示してから追加する。人工入力ボタンの値で補完しない。 |
| ON/OFF判定一致 | 独立した実RUN間のGPS列は異なる。ONで記録した入力・境界を用い、同じ現行判定を診断OFFでPC上に再生し、記録された判定・点選択と比較 | 同一入力についてmismatches=0。別々のOFF/ON実RUNのGPS座標や停止回数の完全一致は要求しない。実行順序とGPS品質の差を付記。 |
| 電池 | Dの各区間で開始/終了残量、取得可能ならcharge counter、経過時間を記録。USB給電を伴う接続中の値は消費比較から除外 | OFFの消費率が分解能を上回る場合、ON増分はmax(1パーセントポイント/時, OFF消費率の20%)以下を暫定目標。短時間・端末%分解能で区別できない場合は判定保留。 |
| 温度 | 実電池温度を開始・終了と取得可能な時点で記録。外気温・充電状態・thermal statusも取得 | 同等条件のON上昇分がOFFより3℃を超えない。電池温度とCPU温度を混同しない。 |
| メモリ | dumpsys meminfoのPSSとNative/JVM値を同じ頻度で取得。開始/中間/終了/終了5分後を最低点とする。電池試験では接続観測の影響を別に記録 | ONの定常PSS増分はOFFに対しmax(30MiB,20%)以下を暫定目標。終了後も増加し続けない。OOM/ANRなし。全時間ピークを採れなければ最大サンプルと表記。 |
| 容量 | セッションbyte、種別recordBytes、Native pending高水位、空き容量を確認 | 診断の64MiB/256MiB上限内。正常完走を要求するRUNで上限拒否が出たら容量評価は不合格。実GPSのbyte/入力と採取可能時間を再推定。 |

電池比較と高頻度ADB監視は別の測定ラウンドにする。未接続中に取得できないメモリ・温度サンプルを推測して補わない。十分な位置精度を確保できない場合は計測を保留して環境を記録する。

## 5. 終了・強制終了・再起動の試験

A/Bの合格後、各ケースを別の新規Test RUNで実施する。通常終了以外は診断が不完全になることを期待する。

1. 通常の途中終了。2〜3分の実GPS後に通常終了し、終了flush・END・seal・SQLite履歴を検証。停止後に入力や音声が追加されないことを確認。
2. 手動一時停止と再開。既存の操作だけを使用し、境界・停止時間・SQLiteへの保存が同じ現行ロジックで再現されることを確認。実停止の正解ラベルは追加しない。
3. アプリ強制終了。直近checkpoint成功の証跡取得後にTest packageだけをforce-stop。次の起動で診断が自動ONにならず、ENDなしの記録が完全扱いされず、最後の保存済み新規Testドラフトを読めることを確認。強制終了中の位置採取は期待しない。
4. 端末再起動。新規Test RUNのcheckpoint確認後に端末を再起動し、ユーザーによるロック解除後、同じ端末Keystoreで既存のseal済み記録と中断記録を読めることを確認。未保存の末尾と最後の保存済み時刻の差を計測する。
5. 新規Testドラフトの継続が既存UIの復帰操作を必要とする場合は、この計画のレビュー時にその操作範囲も確認する。既存の本人RUNやバックアップの復元は行わない。復帰後の記録は別セッションとして識別し、前の中断記録へENDを追記しない。

合格は、最後に成功したSQLite checkpointまでのデータ保持、既存履歴一致、暗号認証成功、未完了の正しい表示、二重RUNや勝手な再採取なし。末尾の損失秒数・件数は実測し、暫定10秒以内を目標とする。checkpoint後の未保存データまで全保持と報告しない。再起動後のRUN継続方法に設計上の疑問が出たら仕様を変更せず報告する。

## 6. 診断障害の隔離試験

通常RUN中に診断をOFFにする操作と、診断の受付拒否は別ケースで確認する。v30の「受付拒否」ボタンは人工入力専用であり、実GPS RUNの障害検証としては使用しない。

実GPS中の障害注入には、Test限定・指定した新規RUNだけ・一回限りの診断offer拒否または診断ファイル書込み失敗を起こす最小限の検証手段を別途提示する。判定・GPS・SQLiteの呼出しには触れず、既存暗号文・鍵・RUNを破損させない。端末ディスクを満杯にする方法やKeystore鍵の削除は使わない。この計画のレビュー後に具体的な追加差分を作成する。

障害前に最低60入力、障害後に最低120入力を実GPSで取得し、通常RUNの判定・GPS点・checkpoint・正常終了保存が継続することを確認する。診断はINCOMPLETE、失敗理由と保存成功件数が一致し、無制限再試行や自動再採取がないこと。失敗後のRUN全体の判定を照合するには採取済み診断だけでは足りないため、既存の通常RUN診断とSQLiteを使い、取得できない全件のdigest一致は未評価とする。必要なら承認済みTest集計を併用する。

## 7. 中止条件と中止手順

以下を検出したら当該ケースを中止し、後続段階へ進まない。

- 既存RUN/GPS/ごみ箱/グループ/保護情報に未説明の差分、履歴消失、SQLite整合性違反、保存失敗。
- ANR・クラッシュ、RUN操作が10秒以上応答しない、Repository待ち5秒超が3回続く、通常保存が30秒以上進まない。
- OSから実GPSが配信されているのに診断INPUTや判定・保存が進まない。良好な受信環境で30秒以上の未説明の配信空白。Doze区間ではOS制限として記録し、解除後の回復確認へ切り替える。
- 診断受付拒否、pending制限到達、セッション容量が上限の90%に到達、端末空き容量が開始時に1GiB未満または試験中512MiB未満。容量上限を増やして試験を継続しない。
- 電池20%以下、実電池温度42℃以上、thermal statusがSEVERE以上、OOM、持続的なメモリ増加、端末の異常発熱、ユーザーの体調や周囲の安全上の問題。

通常RUNが操作可能なら安全な場所で診断をOFFにし、通常操作で新規Test RUNを終了・保存する。RUNが応答しない場合は強制終了や復元を重ねず、取得済み証跡を保持して原因を報告する。強制Dozeを解除し、試験で使った模擬battery状態があればresetする。ロック解除はユーザーに依頼する。既存データの修復・削除は中止処理に含めない。

PRに載せるのは座標・経路・RUN識別子・鍵・原ログを除いた集計と検証方法。生GPS、Backup、診断原文、詳細時刻は私有領域に保持する。実行前にこの計画のレビューを受け、A→B→C→D→Eの各段階で合格を確認する。未測定やOS由来と切り分けできない項目は未受入として残す。
